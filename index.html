1 · Package overview

What this package is
@wordpress/data is the centralized state management layer that powers the WordPress editor. It provides a Redux-based store system wrapped in a registry abstraction, plus selector memoization, resolver-driven async fetching (side effects fired automatically when a selector is called), and a full React integration (hooks, HOCs, context providers). Every higher store (core/blocks, core/editor, core/block-editor, core/edit-post, core) is built on top of this package.

What it truly owns:

  • The registry abstraction — an isolated container holding many named stores (registries can nest for scoped editor contexts).
  • The store descriptor (createReduxStore) and the live Redux store instances it produces.
  • The metadata / resolver subsystem that tracks selector resolution state and drives async data fetching.
  • The middleware stack (promise, thunk, resolvers-cache) and the built-in controls.
  • The React bindings: useSelect, useDispatch, useRegistry, providers, and HOCs.
  • The persistence plugin for saving store state to browser storage.

	emitter.resume();

createReduxStore( key, options ) · src/redux-store/index.ts ★★★ (core factory)

Purpose / why used: Creates a store descriptor ({ name, instantiate }) — not yet wired to a registry. On instantiate(registry) it builds the full live Redux store with the metadata reducer, the middleware stack, resolver integration, and bound actions/selectors.

When used: By every store definition in the editor (core, blocks, editor, block-editor, edit-post, etc.).

Who uses it: All package store modules; the global registerStore convenience.

Inputs: key (store name), options (ReduxStoreConfig: reducer, actions, selectors, resolvers, controls, initialState). Output: a StoreDescriptor.

export function createReduxStore( key, options ) {
	const privateRegistrationFunctions = {
		registerPrivateActions: ( actions ) => { privateActions = actions; },
		registerPrivateSelectors: ( selectors ) => { privateSelectors = selectors; },
	};
	const privateActions = {};
	const privateSelectors = {};

	const storeDescriptor = {
		name: key,
		instantiate( registry ) {
			const thunkArgs = { registry, dispatch, select, resolveSelect };
			const store = instantiateReduxStore( key, options, registry, thunkArgs );
			// ... bind actions & selectors, override getState, subscribe, resolvers ...
			return { reducer, store, actions, selectors, resolvers,
				getSelectors, getResolveSelectors, getSuspendSelectors, getActions, subscribe };
		},
	};
	lock( storeDescriptor, { privateRegistrationFunctions } );
	lock( storeDescriptor.instantiate, { privateRegistrationFunctions } );
	return storeDescriptor;
}

function fulfillSelector( ...args ) {
	if ( resolversCache.isRunning(...) || resolutionStarted(...) || isFulfilled(...) ) { return; }
	resolversCache.markAsRunning( selectorName, args );
	setTimeout( () => {
		dispatch( { type: 'START_RESOLUTION', selectorName, args } );
		Promise.resolve( resolver.fulfill( ...args ) )
			.then( ( action ) => { dispatch( action ); dispatch( { type: 'FINISH_RESOLUTION', selectorName, args } ); } )
			.catch( ( error ) => dispatch( { type: 'FAIL_RESOLUTION', selectorName, args, error } ) )
			.finally( () => resolversCache.clear( selectorName, args ) );
	} );
}

combineReducers( reducers ) · src/redux-store/combine-reducers.ts ★

Purpose / why used: Custom reducer combiner with referential stability (returns old state if no slice changed).

When used: Wherever combineReducers is imported from @wordpress/data.

Who uses it: Store definitions and the metadata/root combiner.

Inputs: a map of reducers. Output: a combined reducer.

export function combineReducers( reducers ) {
	const keys = Object.keys( reducers );
	return function combinedReducer( state = {}, action ) {
		let hasChanged = false;
		const nextState = {};
		for ( const key of keys ) {
			const reducer = reducers[ key ];
			const prev = state[ key ];
			const next = reducer( prev, action );
			nextState[ key ] = next;
			hasChanged = hasChanged || next !== prev;
		}
		return hasChanged ? nextState : state;
	};
}
keyedReducer( actionProperty ) · src/redux-store/keyed-reducer.ts ★★

Purpose / why used: Higher-order reducer that partitions state by a property on the action. If action[actionProperty] is undefined, state is returned unchanged.

When used: By the metadata reducer to key resolution state by selector name.

Who uses it: metadata/reducer.ts.

Inputs: an action property name. Output: a wrapped reducer.

export function keyedReducer( actionProperty ) {
	return function keyed( reducer ) {
		return function keyedReducer( state = {}, action ) {
			const key = action[ actionProperty ];
			if ( key === undefined ) { return state; }
			const innerReducer = reducer( state[ key ], action );
			if ( innerReducer === state[ key ] ) { return state; }
			return { ...state, [ key ]: innerReducer };
		};
	};
}

1 · Package overview

What this package is
@wordpress/blocks is the block API — the foundation of the block editor. It provides the three pillars of block handling: registration (registerBlockType and friends — how a block type is declared), parsing (block boundaries and attributes are inferred from the HTML source of a post and turned into in-memory block objects), and serialization (the in-memory block state is deflated back into an HTML string with invisible comment delimiters). It also provides block transforms, validation, raw/paste handling, block categories, the core/blocks store, and templates.

What it truly owns:

  • The block type registry (core/blocks store) and the public registerBlockType API.
  • The block object factory (createBlock, cloneBlock, ...) and the transform engine (switchToBlockType).
  • The parser pipeline (parse) — HTML → block tree.
  • The serializer (serialize/serializeBlock) — block tree → HTML with comment delimiters.
  • Block validation (validateBlock, isValidBlockContent) and deprecation handling.
  • Raw/paste handling transforms arbitrary HTML into blocks (rawHandler, pasteHandler).
  • Templates, categories, and the children/node BlockNode helpers.

1 · Package overview

What this package is
@wordpress/rich-text is the foundational package for representing, creating, manipulating, serializing, and rendering formatted (rich) text in the block editor. It provides a data model (RichTextValue) that separates plain text from per-character format metadata, a pure-functional API for transforming values (insert, remove, apply/toggle/remove formats, concat, slice, split, join, replace), DOM serialization round-trips (create parses HTML/DOM into a value; toHTMLString and toDom serialize back), a Redux store (core/rich-text) for format-type registration, and React hooks (useRichText, useAnchor) that bridge the model to a live contentEditable element.

What it truly owns:

  • The RichTextValue data model (text + parallel formats/replacements arrays + selection).
  • The pure value-transform functions that are the building blocks of the RichText block.
  • The DOM ↔ value round-trip (create, toDom/apply, toHTMLString).
  • The format-type registration store (core/rich-text).
  • The useRichText hook and the event-listener set that keeps the model in sync with a live editable DOM.

function updateFormats( { value, start, end, formats } ) {
	// normalize start/end (may be swapped on delete)
	for ( let index = start; index < end; index++ ) {
		// reuse refs when equal to neighbors
		if ( isFormatEqual( formats, value.formats[ index - 1 ] ) ) { value.formats[ index ] = value.formats[ index - 1 ]; }
		else if ( isFormatEqual( formats, value.formats[ index + 1 ] ) ) { value.formats[ index ] = value.formats[ index + 1 ]; }
		else { value.formats[ index ] = formats; }
	}
	value.activeFormats = formats;
}

function normaliseFormats( value ) {
	const newFormats = value.formats.slice();
	newFormats.forEach( ( formats, index ) => {
		if ( formats ) {
			formats = formats.map( ( format ) => newFormats[ index - 1 ]?.[0] && isFormatEqual( format, newFormats[ index - 1 ][0] ) ? newFormats[ index - 1 ][0] : format );
			if ( newFormats[ index - 1 ] && isFormatEqual( formats[0], newFormats[ index - 1 ][0] ) ) { newFormats[ index ] = newFormats[ index - 1 ]; }
			else { newFormats[ index ] = formats; }
		}
	} );
	return { ...value, formats: newFormats };
}

1 - Package overview

What this package is
@wordpress/core-data is the data layer for WordPress entities. It is the bridge between the Redux store system (@wordpress/data) and the WordPress REST API. It defines every entity the editor works with (posts, pages, media, taxonomies, templates, patterns, users, global styles, and more), provides the core store with a normalized, query-indexed cache of entity records, and exposes the canonical getEntityRecord / getEntityRecords / editEntityRecord / saveEntityRecord family plus undo/redo, permissions, and (behind an experiment) real-time collaboration.

What it truly owns:

  • The entity registry: rootEntitiesConfig + lazy additionalEntityConfigLoaders (post types, taxonomies, site) that define how any REST resource is treated as an entity.
  • The normalized queried-data cache (queried-data/) - items stored by context+id, indexed by query, with pagination and field filtering.
  • The canonical CRUD selectors/actions/resolvers (getEntityRecord(s), editEntityRecord, saveEntityRecord, deleteEntityRecord, saveEditedEntityRecord).
  • Undo/redo via the @wordpress/undo-manager, and an in-memory locking engine (locks/) used by the editor's save flow.
  • Permissions (canUser via OPTIONS), autosaves/revisions, and the user/theme/pattern sub-caches.
  • The React hooks (useEntityRecord, useEntityRecords, useEntityProp, ...) and the EntityProvider React context.
  • The collaboration (CRDT/Yjs sync) subsystem and the EntitiesSavedStates save panel (both gated).

export function getMergedItemIds( itemIds, nextItemIds, page, perPage ) {
	const nextTotalIds = nextItemIds.length;
	const mergedItemIds = [ ...itemIds ];
	for ( let index = 0; index < nextTotalIds; index++ ) {
		const id = nextItemIds[ index ];
		const nextIndex = ( page - 1 ) * perPage + index;

1 - Package overview

What this package is
@wordpress/components is the shared UI component library used across the WordPress block editor, the site editor, and WordPress Core. It ships roughly 90 reusable components (buttons, forms, modals, popovers, color pickers, toggles, panels, toolbars, tooltips, and more) plus the Context System that lets a parent inject default props into any component by namespace, a set of higher-order components, a Slot/Fill composition system, and design tokens via the utils/ package.

What it truly owns:

  • The Context System: ContextSystemProvider, contextConnect(), useContextSystem(), and the polymorphic as rendering (PolymorphicElement).
  • The full component inventory organized into one folder per component (each with index.tsx, types.ts, style.scss, README.md, and often hook.ts/component.tsx).
  • Design utilities in utils/: colors, fonts, breakpoints, spacing, RTL, motion, math.
  • The Higher-Order Components in higher-order/: navigate-regions, withConstrainedTabbing, withFallbackStyles, withFilters, withFocusOutside, withFocusReturn, withNotices, withSpokenMessages.
  • The SlotFill system (slot-fill/): Slot, Fill, createSlotFill, SlotFillProvider.
  • The newer Ariakit-based composed components (private): Menu, Tabs, Composite, Badge, and the validated form controls.

Where it fits: components is arguably the most reused package; nearly every other UI package (block-editor, edit-post, edit-site, editor) depends on it. It has no Redux store of its own; its "state" is React context, controlled props, and DOM. It is also being progressively migrated: newer components are being built for @wordpress/ui, which supersedes components for new work.

function useContextSystem( props, namespace ) {

	const propsWithContext = { ...contextProps, ...props };
	// apply overrides last: props._overrides?.[ namespace ]

What this package is
@wordpress/block-editor is the generic, WordPress-agnostic middle layer of the three editor layers (block-editor (generic) -> editor (WP post-type-aware) -> edit-post / edit-site (full screens)). It owns the entire block editing surface: the core/block-editor Redux store that models the block tree, selection, and editing state; the Block Supports / hooks system that turns a block type's declared supports into CSS classes, styles, and inspector UI; the canvas (BlockList, BlockListBlock, BlockTools, WritingFlow, iframe); the inspector / toolbar / settings surfaces; the inserter; the list view; rich-text editing, drag-and-drop, link/media handling, and block layouts.

What it truly owns:

  • The store (core/block-editor): the block tree (blocks slice), selection, editing modes, typing/dragging flags, settings, preferences, and template validity.
  • The Block Supports system (hooks/): every editor.BlockEdit / editor.BlockListBlock filter that injects per-support UI and markup.

What this package is
@wordpress/edit-post is the classic post editor screen in wp-admin. It is the highest layer of the three editor layers (block-editor (generic) → editor (WP-aware) → edit-post (full screen)) and owns the bootstrap (initializeEditor), the root layout (Layout), the meta box subsystem, the entity navigation stack, and the browser URL sync. Most of its Redux store is now deprecated wrappers that delegate to @wordpress/editor, @wordpress/interface, @wordpress/preferences, and @wordpress/core-data.

What it truly owns today:

  • The boot sequence (initializeEditor) that mounts the whole editor.
  • The root Layout component that assembles every other screen part.
  • The meta box subsystem (the only Redux state this store really keeps: metaBoxes).
  • The entity navigation stack (post ↔ template / pattern navigation).
  • The browser URL sync and the classic-revision redirect.
  • Legacy SlotFill re-exports in deprecated.jsx for backward compatibility.

	const preloadedResolutions = preloadResolutions( postType, postId );

function mergeMetaboxes( metaboxes = [], newMetaboxes ) {
	const mergedMetaboxes = [ ...metaboxes ];
	for ( const metabox of newMetaboxes ) {
		const existing = mergedMetaboxes.findIndex( ( box ) => box.id === metabox.id );

	async ( { registry, select, dispatch } ) => {

			document.querySelector( '.metabox-base-form' )

			.getEditedEntityRecord( 'postType', postType, postId );

			post.comment_status ? [ 'comment_status', post.comment_status ] : false,
			post.ping_status ? [ 'ping_status', post.ping_status ] : false,
